# Accelerate onboarding prototypes

Start with `onboarding-routes.html`. Route A is `onboarding-flow.html`; Route B is `onboarding-studio.html`. Route C is `onboarding-finder.html`, the lighter existing-block finder. Open directly or serve this directory with a static HTTP server. No package installation, build or backend is required. The prototypes use Accelerate's purple, neutral admin surfaces and triangle mark with a simplified WordPress backdrop.

The ambition is **your first improvement, already prepared**. A and B put an inspectable draft before optional launch setup. C points to existing candidates and hands the user into editing, without generating or creating a block. See [Route C’s scope and pressure test](onboarding-finder.md).

## Route A: Accelerate prepares; the owner steers

1. Confirm the analysis URL and choose assisted preparation or a manual starting point. The entry shows a labelled example and explains what preparation would read.
2. Follow named simulated preparation milestones, or use available content immediately. Optional discovery attribution appears only in the connected entry.
3. Arrive directly at the prepared draft. Compare original/proposal, try a narrow preview, edit the headline, or optionally refine the business brief, direction or page. These are refinements, not required onboarding questions.
4. Keep the draft for later, or review setup. Website entry asks for a matching production WordPress connection after the draft is visible. An admin-pending or failed connection preserves it.
5. Review the exact heading, invitation and supporting-content changes, placement, audience, supported link-click goal and recovery. Resolve shared-pattern, stale-source or unmapped-content blockers, then approve this specific proposal.
6. Separate verified publish from valid visitor exposure. A failed-publish example explicitly simulates transactional rollback; this is a required future contract, not existing backend proof.
7. Return when useful evidence exists. Diagnose no exposure, consent or collection problems; small samples never declare a winner. Pause/resume tests, or restore either type. A next services draft keeps the first live experience separate.
8. Save/reload/resume through the optional setup hub. Hide/show its four milestones or reopen the introduction. Nothing publishes by skipping setup.

The top navigation is a reviewer tool, not a mandatory eight-step wizard. Direct jumps into live/return screens load labelled simulated fixtures. They must never count as real product activation.

## Route B: the website is the workspace

1. Open on a recommended treatment already rendered on the page. Compare with Original as a short learning-by-doing prompt. Review is available before changing any defaults.
2. Optionally choose the introduction or how-we-work section, another complete treatment, or a recorded migration campaign audience. Edit manually from the prepared treatment or original content. Further assisted suggestions require an explicit opt-in.
3. Review the exact before/after copy beside the canvas. Scope/content changes clear approval. An unchanged manual draft cannot launch.
4. Resolve the reviewer scenarios for access pending/denied, connection failure, staging, shared patterns, stale source, unmapped content, unavailable generation or no cached draft. The last path returns to original content for manual editing.
5. Approve and simulate launch. Failed verification leaves status unknown; an explicit installation check is required before retrying with fresh approval. The simulation then reports the original unchanged.
6. Inspect exposure, test pause/resume, collection diagnosis and the return view. A live experience stays locked until explicitly restored. Campaign personalisation has no assumed working pause control.
7. Skip or save to a local overview, reload, resume, or rerun draft setup. The four optional milestones reflect the current proposal rather than historical completion.

The studio models plugin entry. A public website entry is a documented future extension, not an implemented second entry route.

## Evidence and implementation boundaries

Northstar Studio, site content, scans, checks, counts and notifications are fictional. Changing a URL changes the analysis label; it does not fetch that business. No external provider requests, WordPress mutations, email, pricing decisions or analytics transmission occur. Browser storage preserves prototype state where available; if storage is unavailable, the current session works but persistence is not guaranteed.

The local receipts keep bounded action names and fixed scope labels. They are not server audit logs. Optional attribution text is separate from general events. A demo `first_value_reached` event only records reaching the prepared fixture, not that a customer judged a real-site draft useful.

Production still needs authenticated site identity, bounded analysis, safe editable-placement mapping, draft preparation, full-page previews, supported goal mapping, consent-aware measurement, concurrency-safe publishing and complete recovery. Existing `create-ab-test` starts a test immediately; it is not a draft API. Provider keys stay on the hosted service and generation never receives publishing authority.

First draft, setup completion and valid exposure are different milestones. The proposed activation candidate is an intentionally approved experience receiving valid eligible non-preview exposure within seven days. Its relationship with retention remains unvalidated. Personalisation provides relevant targeting, not causal lift. Return timing follows useful evidence, not a promise of a winner after 48 hours or seven days.
